## R1 · P1：可写命令目录与跟随链接的临时文件组合，可覆盖其他文件

位置：[ellekit_bridge.py](../../src/ios_control_bridge/ellekit_bridge.py) 第 35–40 行；[build_ellekit_bridge.py](../../tools/build_ellekit_bridge.py) 第 64 行；[SpringBridge.m](../../native/ellekit/SpringBridge.m) 第 200–208 行。

安装器把共享目录设为 `0777`，客户端对固定路径 `spring.cmd.tmp` 调用 `write_text`。任意能访问该目录的本地进程可预置符号链接；当 root 运行 `iosctl` 时，写命令会先截断链接指向的文件，随后的 `os.replace` 已无法保护原文件。SpringBoard 的 `fopen(RESULT_TMP, "w")` 也会跟随链接，权限范围为 SpringBoard 的 mobile 身份。

离线复现只使用临时目录内的自有文件：预置链接后执行一次真实 Python bridge 请求，另一个配置文件确实被覆盖。没有尝试覆盖设备或特权文件。真机检查确认了目录权限这一前提。

修复：控制目录的所有者与访问组，移除 world-write；由设备端验证客户端身份。文件方案至少需要独占创建、拒绝符号链接、检查 fd 的类型/所有者并使用独立请求文件。更适合后续 UI 操作的是有身份验证、请求生命周期和串行队列的本地 IPC。仅加随机 request ID 不构成认证。

另有边界不一致：原生 `execute` 仍接受 `set_bluetooth`（第 228–229 行），Python 和文档却声明蓝牙只读。当前设备上 setter 未生效不能充当长期的只读保障；应移除该原生命令。

## R2 · P2：超时或重载后仍可能执行旧写命令

位置：[ellekit_bridge.py](../../src/ios_control_bridge/ellekit_bridge.py) 第 43–57 行；[SpringBridge.m](../../native/ellekit/SpringBridge.m) 第 41、245–280 行。

客户端超时后保留命令文件；服务端只有内存中的 `last_id`，没有请求过期时间或持久化消费状态。结果是命令可在客户端已经报告超时之后才执行。SpringBoard 重启时 `last_id` 清空，仍在磁盘上的最后一条命令还会被重新识别。若最后一条是方向锁定或低电量写入，它可能覆盖用户稍后选择的状态。

离线调用 `request("set_orientation_lock", 1, timeout=0)` 后，结果为 `bridge_timeout`，写命令仍在。重载后的再次处理由原生控制流直接确定；本轮没有为复现而重启手机。

修复：服务端管理 deadline、已消费状态及启动代次；启动时拒绝遗留请求，执行前重新检查有效性。超时返回“结果未知”并提供按请求 ID 查询状态的途径。不能只在客户端删除文件后就声称已取消，因为执行可能已经开始。

## R3 · P1：创建同名日历或提醒事项，可能返回旧对象 ID

位置：[CalendarBridge.m](../../native/calendar/CalendarBridge.m) 第 148–157 行；[RemindersBridge.m](../../native/reminders/RemindersBridge.m) 第 223–239 行；[calendar.py](../../src/ios_control_bridge/calendar.py) 第 108–114 行。

日历创建的确认条件是“新 ID **或** 同名”，遇到列表中较早的同名旧日历会提前返回；它也可能来自另一个账户。提醒事项创建直接选择保存后第一个同标题条目，没有使用新建 change item 的对象身份，也没有排除已有 ID。

同名条目是合法数据。返回旧 ID 后，后续按“刚创建的条目”执行编辑、完成或清理，可能改动原有用户数据。Python 侧只检查标题，日历侧连显式传入的 `source_id` 也没有核对。离线反例证实：请求 source A、helper 返回 source B，仍被包装为 `verified`。原生重复标题的选择问题来自静态控制流检查，尚未在个人数据中制造重复条目。

修复：保存并读回新建对象的稳定 ID，准确核对 source/list 和请求字段；无法获取唯一身份时返回 `partial`。不能用标题兜底当成创建成功，也不能按同名匹配结果自动清理。

## R4 · P1：Live Activity 正文变化不会触发 watch 的变化检测

位置：[activities.py](../../src/ios_control_bridge/activities.py) 第 91–96、144–152 行；对照 [main.swift](../../native/activities/main.swift) 第 101–103 行。

`_activity_state` 只取 `activity.state`，这是生命周期状态；真正的正文是原生返回的顶层 `content` / `activity.contentState.decoded`。内容从 10 改为 20 而活动仍为 `active` 时，`changed` 仍为 false，`stop_on_change` 不会提前停止，采样中还丢失了正文。

离线复现经过真实 `get_activity` 的 JSON 边界，用两次合法原生响应提供 `content.value: 10 → 20`，结果为 `changed=false`。现有 `test_watch.py` 将测试数值放进了生命周期 `state`，因此掩盖了问题。现有真机证据中的随机不存在 UUID 轮询，也不能覆盖正文变化。

修复：比较包含目标是否存在、生命周期和原始正文的完整投影，保留正文样本；初始“尚未采样”应使用独立哨兵，以识别首次不存在、随后出现的变化。补充保持 active 的正文变化、出现、结束及无变化用例。

## R5 · P2：删除后的查询失败会被当作“已删除”

位置：[AlarmsBridge.m](../../native/alarms/AlarmsBridge.m) 第 124–130、239–242 行；[RemindersBridge.m](../../native/reminders/RemindersBridge.m) 第 112–148、282–285 行。

`find_alarm` 和 `find_reminder` 对“完整查询后不存在”与“服务读取失败”都返回 nil。删除后的确认只检查是否非 nil；若此时 `alarmsSync`、清单读取或某个清单的提醒读取失败，就会返回 `deleted=true/verified`。Python 只核对删除布尔值和 ID，无法恢复丢失的查询错误。

这是原生错误路径的静态确定性问题，本轮没有人为中断手机系统服务来触发它。

修复：查找返回独立的查询完成状态、错误和 found 状态。只有在目标范围完整读取成功且目标缺失时才能确认删除，否则报告 `partial/readback_unavailable`，并让上层避免盲目重试。

## R6 · P2：两个客户端共享一个 mailbox，会覆盖命令和结果

位置：[ellekit_bridge.py](../../src/ios_control_bridge/ellekit_bridge.py) 第 35–40 行。

所有进程使用同一个 `spring.cmd.tmp`、`spring.cmd` 和 `spring.result`，提交前还删除公共结果文件。Codex 与 OpenCode 并发请求时，一个客户端可删除另一个尚未读取的结果，或替换另一个客户端的临时文件。request ID 只能识别错配，不能防止覆盖与丢失。

离线复现控制实际 `os.replace` 的交错顺序：A 写临时文件，B 写入并提交，A 再提交。B 返回 `ok`，A 返回 `bridge_command_write_failed`。没有任何系统设置操作。

修复：设备端单队列处理、每请求独立应答和明确的客户端身份；临时补救也必须使用跨进程锁及唯一临时文件，不能只使用 Python 线程锁。UI 版本还需要设备端独占操作租约，覆盖两个独立 MCP 进程。

## R7 · P2：日历事件截断到 100 条，却声明查询完整

位置：[CalendarBridge.m](../../native/calendar/CalendarBridge.m) 第 171–176 行；[calendar.py](../../src/ios_control_bridge/calendar.py) 第 198–202 行。

原生循环达到 100 条就结束，既不标注 truncated，也不提供分页；Python 对列表一律返回 `complete_for_scope=true`。指定范围有 101 条以上时，调用方会把缺失的事件误判为不存在。

修复：返回准确的截断标记、范围/排序与分页信息，截断时标明不完整；至少保证原生错误和不完整信息不会在 Python 包装时被丢弃。本项为静态检查，本轮没有创建 101 条测试事件。

## R8 · P2：文件搜索吞掉权限错误，返回完整空结果

位置：[files.py](../../src/ios_control_bridge/files.py) 第 135–147 行。

`visit` 捕获 PermissionError/OSError 后直接返回 false，调用方只根据匹配条数判断完整性。根目录或子目录无法读取时，查询仍可能是 `verified`、0 条、`complete_for_scope=true`。

离线对 `os.scandir` 注入 PermissionError，实际结果就是完整空结果。修复应记录失败目录；根目录不可读取返回 unavailable，部分子目录不可读取则返回 partial，并给出有界错误信息。

## R9 · P2：日历事件写入没有验证请求的时间与备注

位置：[calendar.py](../../src/ios_control_bridge/calendar.py) 第 238–244 行；[CalendarBridge.m](../../native/calendar/CalendarBridge.m) 第 66–75、199–201 行。

Python 只核对日历 ID 和标题，未核对 start/end；原生描述也没有返回 notes。离线提供时间为 Unix 0 和 1 的 helper 结果，尽管请求时间为 2026-11-05，仍得到 `verified`。这证明协议边界无法保证“所请求的写入”已读回，不证明正常 EventKit 会主动改错时间。

修复：统一 UTC 时间表示，核对 start/end 与 notes；原生读回缺字段时不能确认完整写入。测试应覆盖时区转换及读回时间/备注不一致。

## R10 · P2：递归搜索结果缺少目录位置

位置：[files.py](../../src/ios_control_bridge/files.py) 第 23–43、127–130 行。

递归搜索将 `_entry` 的返回值直接加入结果，仅有 name、type 等信息，没有 path 或相对目录。两个子目录下的同名文件无法区分，后续也无法用搜索结果可靠调用 `files.read`。离线在子目录创建匹配文件，返回字段确认不含路径。

修复：每个匹配项返回相对于明确搜索根的路径；需要绝对路径时在该根内解析。保留现有不跟随目录符号链接的边界。
